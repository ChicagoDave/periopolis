# Session Plan: Board auto-run month by month with visible progress

**Created**: 2026-10-19
**Plan Status**: DONE
**Overall scope**: Replace the manual Next month tap with a Play/Pause control that advances the run one month per timer step (tickMonth, then render), at a chosen speed, stopping at year 20; make the month clock the Board's default run; reword the buttons; pin it with an e2e flow. Board-only wiring and wording; no domain change.
**Bounded contexts touched**: Board (apps/board) only. Run (domain/run) is read, not changed; docs/domain/run.md gets a note only if the Board's use of the month clock needs recording.
**Key domain language**: month clock (growth), yearly mode, run / clock, orders (placements for the crews), Next year, undo/remember.

## Design decisions the plan carries (confirm with David at the Phase 1 start; they are small)
1. **Play drives tickMonth on a timer.** One step = `tickMonth` + `s.game = next` + `s.save()` + `page.render()` + `page.say(monthLine / yearLine)`, the same body the `month` handler has today, extracted once and called by both the tap and the timer.
2. **Month clock is the default.** Runs start with `growth: true`. The `monthly` checkbox is inverted into an opt-out ("Year by year, as the sketch runs it") so the yearly mode and Next year stay reachable. Parity is unaffected (the suite calls the Run directly with growth off).
3. **Starting a run does not start the timer.** "Run this city" / "Found a city" put the clock at year 0 paused with orders open; the player places orders, then presses Play. This keeps the existing flows and the "orders for the crews" framing.
4. **A placement pauses.** Any edit that changes the layout while playing (place, remove, line, stretch) pauses the timer and says so ("Paused: your order is in. Press Play to carry on."). Tool selection, hover and panning do not pause. This is a Board-side rule, not a Run rule.
5. **Speed.** A three-step control (Slow ~1 s, Steady ~400 ms, Fast ~100 ms a month); changing it while playing re-arms the timer without resetting the month. Speed is Board state, not persisted game state.
6. **Stop at year 20.** The timer clears itself when `clock.year >= RULES.years`, says "The 20 years are up.", and Play hides as `drawClock` already hides tick at the end.
7. **Undo: one remembered state per Play press**, taken at play start, not per month. A 240-month run is one undo step back to where Play was pressed; the manual Next month / Next year taps keep one state per tap. Stop / reload / Run-again also clear the timer.
8. **Reload never auto-resumes.** The timer lives in memory only; storage keeps the clock exactly as today, so a reloaded run is paused in whatever month it reached.
9. **Guards.** `run`, `found`, `stop`, `tick`, `month` and undo all clear the timer first (the Board has no redo) (today a `run` tap mid-run restarts at year 0 with a new seed; with Play this becomes a pause then the restart, which stays undoable).
10. **ADR-worthy**: the default-run change plus pause-on-placement plus one-undo-per-play are decisions a future session must not re-litigate. Ask David at Phase 2; if yes, write ADR-0013 (Kind technical, Scope apps/board) and add a one-line pointer to ADR-0009 Decision 5's consequences.
